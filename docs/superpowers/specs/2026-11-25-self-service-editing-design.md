# 活动策划网站 · 自服务编辑 + 扫码观看 — 设计文档

日期：2026-11-25

## 1. 背景与目标

现有网站是一个单文件静态页 `index.html`，托管在 GitHub Pages（`https://stepc-24.github.io/event-planner/`），二维码 `qrcode.png` 已指向该地址，客户扫码已能查看。

用户需要新增两个能力：

1. **自服务编辑**：让完全不懂技术的同事，通过一个「填表式后台页」自行新增 / 修改 / 删除案例，无需再让开发者手工改代码。
2. **扫码观看**：客户扫二维码即可查看最新内容（此能力现状已具备，本设计保持不变）。

约束：不换平台、不注册新的云账号、不花钱、不备案；继续用现有 GitHub 仓库与二维码。

## 2. 现状

- 案例数据硬编码在 `index.html` 内嵌的 `<script>` 中（`categories` + `styles` 数组）。
- 图片全部使用 Unsplash 外链（国内访问不稳，需支持自传图片）。
- `qrcode.png` 已指向线上地址，无需改动。
- 站点部署：`master` 分支根目录 → GitHub Pages 自动发布。

## 3. 总体方案

把「内容（数据 + 图片）」与「展示（页面）」分离：

- **数据层**：新建 `data.json`，存放全部案例；`index.html` 运行时通过 `fetch` 读取并渲染。
- **编辑层**：新建 `admin.html`（隐藏后台页，密码入口），提供表单式增删改 + 图片上传/粘贴链接。
- **发布层**：后台页通过 GitHub Contents API，把改好的 `data.json` 和图片文件自动写回仓库；GitHub Pages 检测到提交后约 1 分钟自动重新发布。
- **访问层**：二维码与线上地址保持不变。

```
[同事] --填表/传图--> admin.html --GitHub API 提交--> 仓库(data.json + images/) --自动发布--> GitHub Pages --> 客户扫码查看
```

## 5. 数据模型

`data.json` 结构：

```json
{
  "styles": [
    {
      "id": 1,
      "category": "wedding",
      "title": "浪漫海岛婚礼",
      "cover": "images/1-cover.jpg",
      "desc": "……",
      "priceRange": "¥28,888 - ¥68,888",
      "video": "",
      "poster": "",
      "images": ["images/1-1.jpg", "images/1-2.jpg", "images/1-3.jpg"],
      "prices": [
        { "name": "基础套餐", "price": "¥28,888", "items": ["……", "……"] }
      ],
      "tags": ["海岛", "户外", "浪漫"],
      "contact": { "phone": "13800138000", "wechat": "eventplanner123" }
    }
  ]
}
```

- 图片字段既可以是相对路径（上传的自有图片，存于 `images/`），也可以是完整 URL（粘贴的外链）。
- `category` 取值：`wedding` / `birthday` / `corporate` / `party` / `other`。
- `categories`（分类名与图标）保持不变，仍写在 `index.html` 中，因为分类相对固定。

## 6. 后台管理页（admin.html）设计

### 6.1 入口与登录

- 页面加载先弹出密码输入；校验通过后进入管理界面。
- 密码为内置默认值 `admin2026`，可在 `admin.html` 顶部常量中修改；仅作「防误入」的门槛，非强安全。
- GitHub 令牌（token）首次使用时输入，之后存于浏览器 `localStorage`，下次免输入。

### 6.2 功能列表

- **案例列表**：展示每个案例的封面缩略图、标题、分类；提供「编辑」「删除」按钮。
- **新增案例**：空表单，填完保存。
- **编辑表单字段**：
  - 标题、分类（下拉）、描述（多行）、价格区间、标签（逗号分隔）
  - 封面图、轮播图 3 张（每张支持「上传」或「粘贴图片 URL」）
  - 套餐 3 档（每档：名称、价格、服务项列表）
  - 联系电话、微信号
- **图片处理**：上传时在浏览器端用 Canvas 压缩（最长边 ≤ 1280px、JPEG 质量 0.8），减小体积与仓库占用。
- **保存并发布**：点击后显示进度（写图片 → 写数据 → 发布中），成功后提示「约 1 分钟生效」。

### 6.3 交互细节

- 表单校验：标题、分类、封面、至少 1 张轮播图、电话/微信号必填。
- 删除需二次确认。
- 保存失败（如网络、令牌失效、409 冲突）给出可读的中文错误提示。

## 7. 发布流程（GitHub API 写回）

后台页使用 GitHub Contents API（REST）：

1. 读取当前 `data.json`（`GET /repos/stepc-24/event-planner/contents/data.json?ref=master`）获取其 `sha`。
2. 若有新上传的图片：逐张 `PUT /repos/.../contents/images/<文件名>`（content 为 base64）。
3. `PUT /repos/.../contents/data.json`，携带最新内容 + 上一步 `sha`，提交到 `master` 分支。
4. GitHub Pages 检测到 `master` 提交后自动重新发布（约 1 分钟内生效）。

- 仓库、分支、owner 等固定写在 `admin.html` 顶部常量中。
- 令牌要求：**Fine-grained PAT**，范围仅限 `event-planner` 仓库，权限仅 `Contents: Read and write`。

## 8. 安全与限制

- **令牌权限最小化**：只授予单个仓库的 Contents 读写，泄露后影响面仅此一个仓库。
- **密码门槛**：后台页设密码，防止无关人员误入。
- **令牌存放位置**：仅存于用户浏览器的 `localStorage`，不写入仓库、不进入 `data.json` 或 `index.html`。
- **已知局限**：
  - 令牌以明文形式存在于管理页前端代码运行环境中（静态站无服务器）。对于「公司内部小站 + 单仓库最小权限」场景风险可控；如需更强安全，后续可改为 Cloudflare Worker 代持令牌（需另注册账号，暂不做）。
  - 单人在单设备编辑为主，暂不做多人并发冲突处理；若发生 409 冲突，提示刷新后重试。

## 9. 用户需准备的一次性步骤

1. 登录 GitHub（`stepc-24` 账号）。
2. 生成 Fine-grained PAT（截图级步骤届时提供），权限：仓库 `event-planner`、`Contents: Read and write`。
3. 打开 `admin.html`，首次输入该令牌；之后即可正常使用。

> 开发者会在实现时提供逐步截图指引；令牌本身由用户本人生成并仅保存在自己浏览器中。

## 10. 测试计划

- **本地**：`index.html` 能正确读取 `data.json` 并渲染全部案例；图片相对路径/外链均正常。
- **后台**：本地用假数据走通表单校验、增删改、图片压缩逻辑。
- **线上联调**：用户提供令牌后，后台新增一个测试案例 → 提交 → 等待约 1 分钟 → 扫码确认更新生效。
- **回归**：分类筛选、详情页、轮播、电话/微信复制等原有功能不受影响。

## 11. 部署与后续

- 将所有改动推送到 `master`，GitHub Pages 自动发布；二维码不变。
- **可选后续**（本期不做）：若客户反馈国内打开慢，可加免费 CDN 加速，或迁移到国内托管。

## 12. 风险与注意

- GitHub Pages 国内偶有卡顿：现状可用，暂不处理；若影响使用再评估加速方案。
- Unsplash 旧图国内可能不显示：已通过「支持上传自有图片」解决，旧案例可由用户逐步替换为自己的照片。
- `admin.html` 与 `docs/` 会随站点一并公开：两者均不含密钥（令牌仅存用户本地），无敏感信息泄露。
